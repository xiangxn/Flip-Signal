## 1. 三段判定链（现行引擎口径）

每个 5 分钟窗口按**先后顺序**走三段，**任一段出信号即整窗只下一单**，之后不再判定：

```
Watching ──首个有效 tick 且 rem ≤ t150_rem(150) 且 spot 可算──▶ [判 ⑤]
   ├─ OK      → 落信号行（下单）→ Done
   └─ 拒绝    → Await60
                （若首个有效 tick 已在 rem ≤ t60_rem(60)：整段跳过，直接进 Await60）
Await60  ──首个有效 tick 且 rem ≤ t60_rem(60) 且 spot 可算──▶ [判 ⑤]
   ├─ OK      → 落信号行（下单）→ Done
   └─ 拒绝    → Listening
Listening ──此后**每秒**：有效 tick ∧ ② 达标 ──▶ 落信号行（下单）→ Done
   └─ rem == 0 → Done
```

- **T=150 段**：`rem ≤ 150` 的首个可判定 tick 上判一次完整 ⑤。这一段取代了原来的
  「rem≤150 原始帧（只记录）」——**现在它本身就是下单点**，故「原始帧」表下线（§4）。
  ⚠️ **本段的价格腿是严格大于**（`hot_ask > 0.80`，2026-09-26 起，见 §6）；下面 T=60 与监听段
  仍是 `≥`。这是三段之间**唯一**的规则差异。
- **T=60 段**：T=150 段没出信号才判第二次 ⑤（同一套规则、同一批输入，只是时点更晚、价格更高；
  价格腿仍是 `≥ 0.80`）。
- **监听段**：前两段都没信号时，从 T=60 之后的**下一个** tick 起每秒判 **②**：
  `hot_ask ≥ 0.80 ∧ dev ≥ 63 美元`（**不含 σ 腿**）。达标即下单。监听段的**拒绝 tick 不落行**
  （每窗约 60 个 tick，全落会淹没信号表）。
- **有效 tick 判据（§2 之后）**：`BookLatMs ≤ tail.max_book_lat_ms` ∧ 热门侧有效价 > 0。
- **缺 spot 的 tick 不推进任何段、不落行**，等下一个可判定 tick（与监听段同一原则）。
  与旧口径「缺 spot 整窗丢弃」的差异在历史数据上是 **0 窗**（§5），取更稳的那条。
- **锚不变量不变**（决策 #15）：窗口开局 `BeginWindow(0,0)` 不设过渡锚，锚 = 边界那一秒的
  推送，`UpgradeAnchor` 在**本窗首行落盘后**拒收；**无锚 ⇒ 本窗一行不产出**。
- **崩溃重启续跑**：`Engine.Resume(t150Done, t60Done)` 按磁盘真相回填已完成段与状态
  （两个都完成 ⇒ Listening），`emitted` 保持 false（否则 `UpgradeAnchor` 被自己的冻结判据挡死、
  锚永远进不来）。重启后锚由同一条边界推送确定性重取，与旧行基准同源。
- **防双单**：`cmd/tail` 重入同一窗口时，只要该窗**已有 OK 行**（`Recorder.HasSignal`）就整窗跳过；
  若只有拒绝行则续跑（由 `Resume` 回填段闩锁，不会重复判定同一段）。

### 1.1 判定行 vs 信号行

| 行 | 何时产出 | 字段 |
|---|---|---|
| 判定行（`stage = t150` / `t60`） | 每段各一条，**成功与否都落盘** | `rules` 四腿 + `ok` + `reject_reason` + `shares` |
| 信号行（`stage = t150` / `t60` / `listen`） | 判定通过（= 上表中的 `ok = true` 行） | 同上 + 执行/结算段 |

- 行类型**不新增 kind**：一律 `kind = "snap"`（沿用落盘 schema 与 legacy 兼容），
  新增 `stage` 字段区分三段。`kind = "frame" / "scan"` 成为 **legacy-only**（`isKnownKind`
  仍认、引擎不再产出）。
- 拒绝原因链去掉 `missing_twap`（⑤ 不用 twap）：`missing_spot → no_hist → price_low → leg_out`。
  `price_low` 的判据**随段而变**（T=150 段 = `有效价 ≤ 0.80`，其余段 = `< 0.80`，见 §6）——
  行里的 `rules.price` 与它自洽：`price = false` ⇔ `reject_reason = price_low`。
  `missing_spot` / `no_hist` 与前文同性质，是**纯函数防线**（现网由 §1 的「跳过无 spot 的 tick」
  与 `cmd/tail` 的 `skip=no_sigma` 整窗闸挡在前面）。

## 2. 空侧口径：ask 优先、bid 兜底

**背景（决策 #21）**：行情一边倒时赢家侧的 ask 会被整侧撤空（实盘探针 4 窗，rem = 12/28/45/47），
旧实现把「ask 为空」当整簿无效 → 该 tick 直接丢弃（旧旧版更糟：留冻结簿造出假 0.99）。

新口径（用户决定）：

- **每侧有效价** = `ask > 0 ? ask : bid`；**热门侧 = 有效价高的一侧**（平局取 yes）。
- **计算用它**：价格腿 `有效价`（T=150 段 `> 0.80`、其余段 `≥ 0.80`，见 §6）、
  股数 `stake / 有效价`、`hot_ask` 字段 = 有效价。
- **下单用它**：live 的 GTC 限价 = 有效价（ask 为空时即以 bid 挂单）。
- **tick 有效性**：只要有**任意一档**报价 > 0 就是有效 tick（四档全空才算无效）。
- 落盘增 `hot_src ∈ {ask, bid}` 审计字段——一眼看出这一行的价格腿吃的是哪一侧。

⚠️ 已知口径差（写进 dashboard 与本文档）：**ask 为空、按 bid 成交**的窗口，paper 仍按
「限价即成交」记账（偏乐观），live 实际是挂单等成交、大概率不成交。故此类信号在纸面上会
系统性好于实盘，`hot_src = bid` 的行数应当始终在信号表里单独可见。

## 3. 结算与分类口径

1. **所有信号都注册结算**：`isSettlable` = `kind = snap（含 legacy scan）∧ ok ∧ 未结算 ∧ conditionID 非空`，
   唯一排除项是**未定稿**的 `submitting` / `resting`。因此被闸行、下单被拒行、0 成交行
   也会拿到官方 outcome 并在页面上显示赢/输。
2. **未成交不计算 P&L**：结算时
   `if !HasPosition() { pnl = 0 }`，成交行照旧 `赢 = shares − cost` / `输 = −cost`。
   `DailyPnl` / `MaxDrawdown` / `LiveSummary` 的 P&L 段全部加 `HasPosition()` 过滤
   ⇒ 未成交行**不动日亏熔断、不进回撤、不进累计 P&L**。
   - ⚠️ **判据是 `HasPosition()` 而不是 `IsFilled()`**：两者差在 legacy 的 scan 对账行
     （`Kind == KindScan`）——它**恒无仓位**（从不下单），但 `ExecStatus` 为空又会被
     `IsFilled()` 判成「paper 模拟成交」。只按 `IsFilled()` 过滤会让历史目录里的 scan 行
     混进胜率与 P&L。`HasPosition() = Kind != KindScan ∧ IsFilled()`，是**胜负分类与
     P&L 聚合的唯一准入判据**（dashboard 的 tally 与逐日表共用它）。
3. **被闸行口径变更（tail 的方案 A 作废）**：a.md 把「被风控拦」明确归入**未成交**，
   故 paper 与 live 统一成一个 rejected 形态（`exec_status = rejected` + `gate_reason`）——
   paper 被闸行不再算持仓、不进胜率与 P&L。**日亏熔断的锁存判据不变**
   （`Recorder.GatedOn`，磁盘真相，重启/跨日自动恢复/归零）。
   ⚠️ 代价：paper 不再保留「当日不熔断会怎样」的反事实样本（flip 侧不受影响，仍是方案 A）。
4. **分类恒等式**（Dashboard 与逐日表共用）：

   ```
   signals = won + lost + pending + noexec
   won / lost / pending  要求 HasPosition()（pending = 已成交、等结算回填）
   noexec = ok ∧ ¬HasPosition()（被闸 / 下单被拒 / 0 成交 / 挂单未定稿）
   ```
   胜率分母**只含 won + lost**；未成交行不计入（a.md 第 4 条）。
5. **竞态**：resting 行可能先被结算（闭市 +10s）后由 FillTracker 定稿——`Resolve` /
   `CompleteExecution` / `CompleteRestingFill` 共用 `recomputePnL`，定稿时若已结算会**补算** P&L，
   否则会出现「成交了却永远 0 盈亏」。

## 6. 2026-09-26 · T=150 段价格腿改为严格大于（`> 0.80`）

**改动（用户决定）**：**只有 T=150 段**的价格腿从 `≥ 0.80` 变成 **`> 0.80`**；T=60 段的 ⑤
与监听段的 ② **一字不改**（仍是 ≥）。实现 = `internal/tail.PriceLeg`（本包**唯一**的段相关腿，
`EvalRules` 按段取比较符）＋ oracle `23_tail_integrated.py` 的 `r5(strict_price=True)`。

⚠️ 这一格不是浮点边界：报价落在 **0.01 的 tick 网格**上，`hot_ask == 0.80` 是**常态形态**
（14 天里 t150 行有 50 条落在这一格）。所以这是确定的、可逐位对账的口径取舍，不是舍入问题。

### 6.1 依据：0.80 是两个样本里唯一负 EV 的价格档

**实盘**（`data/tail-live`，09-24~09-25，**真实 GTC 挂单**，stake 10U，205 笔信号合计 +55.78U）：

| 入场价 | n | 胜率 | P&L | EV/笔 |
|---|---|---|---|---|
| **= 0.80** | **4** | **50.00%** | **−14.38U** | **−3.5938U** |
| 0.81~0.85 | 10 | 90.00% | +9.34U | +0.9345U |
| 0.86~0.90 | 25 | 100.00% | +31.23U | +1.2492U |
| 0.91~0.95 | 37 | 97.30% | +26.53U | +0.7170U |
| 0.96~0.99 | 126 | 99.21% | +3.05U | +0.0242U |

4 笔 0.80 全在 t150 段，实际成交价 0.76 / 0.80 / 0.80 / 0.79（挂单吃到了价格改善），
结果 赢/输/赢/输 —— **其余 201 笔的胜率是 98.51%**。

**14 天回测**（2U/注，同一分桶）：0.80 档 n=17 WR 76.47% **−1.50U**（EV −0.0882U/注）——
它是整条价格梯度上**唯一的负 EV 档**；0.81~0.85 起转正（+0.0299U/注）。
分到段上：t150 恰好 0.80 的 12 笔是 **+1.00U**（不是负的）、t60 1 笔 +0.50U、listen 4 笔 −3.00U。

**两样本的一致性**：都说 0.80 是最差档（实盘 −14.38U / 回测 −1.50U）。⚠️ 但两边样本都很薄
（4 笔 / 17 笔），**真正的共同点只是「它是最差档」这一条排序**，不是「它亏 14U」这个量。
