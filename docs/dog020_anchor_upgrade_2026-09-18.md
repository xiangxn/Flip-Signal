## 0. 结论速览（TL;DR）

| 项 | 改前 | 改后 | 依据 |
|------|------|------|------|
| 锚的取值口径 | 边界瞬间 `Latest()` = **最新到达**的那条推送，实际是「边界前那一秒」的评估值 | t=0 仍用 `Latest()` 占位，**+1s 起每秒**按**评估时刻**从缓存重选，官方 open 取到即终局 | 官方 open = 边界那一秒的评估值，它在边界后 ~1.6s 才到达；两者差 p90 **0.24bps**、\|差\|>0.5bps 占 **7.3%**（§1） |

## 1. 问题：t=0 的「最新到达」系统性偏一档（实测）

### 1.1 WS 原始探测（`wss://ws-live-data.polymarket.com`，topic `crypto_prices_twap_sixty`）

| 观察项 | 实测 |
|--------|------|
| `payload.timestamp` 语义 | **TWAP 评估时刻**，落在**整秒格**上（如 `...954000`），非到达/发布时刻 |
| `payload.value` | 该评估时刻的 Chainlink TWAP-60 值 |
| 信封 `timestamp`（发布时刻） | 评估时刻 + **1.0~1.5s** |
| 推送频率 | ≈ 1 条/s |

→ 窗口边界（本地整秒）**当场**能拿到的最新到达条目，评估时刻是 `边界 − 1s`（±1s 抖动）；
**边界那一秒**的评估值要等 ~1.6s 才到。

### 1.2 3753 个回测窗口对账

把每个窗口的官方 `openPrice` 与流值推送逐一比对：

| 指标 | 值 |
|------|-----|
| 官方 open **逐位浮点相等**于某条推送 | **1717 / 3753 = 45.7%** |
| 相等条件下的推送**到达时刻 − 边界** | p10 **+1.27s** / p50 **+1.64s** / p90 **+2.28s** |
| t=0「最新到达」口径 vs 官方 open 的差 | p90 **0.24bps**；\|差\| > 0.5bps 占 **7.3%** |

即：官方的 `openPrice` **就是边界那一秒的推送值**，只是发布比边界晚 ~1.6s。

09-16 那篇报的是 **p50 0.056bps**——本次逐窗重算的 p50 同量级，**差别在尾部**：
p90 0.24bps、|差|>0.5bps 占 7.3%。`cmd/flip/main.go` 旧注释据此写下「等价」，
**低估了尾部**（浅洞带进出对 0.5bps 量级敏感），故本次改为按分布落盘（§4）。

#### 1.2b 独立复核：按**到达序列**重建（不依赖本改动的新代码）

记录数据里没有推送的评估时刻，但 `到达时刻 = tick.ts − twap.age_ms` 可精确重建
「哪一刻到了哪条推送」。对每个窗口边界后的第 1/2/3 条到达分别与官方 open 比：

| 对照 | 占比 | 差值 |
|------|------|------|
| 官方 open == 边界后**第 1** 条到达（到达 p50 +0.91s） | 22.6% | 逐位相等 |
| 官方 open == 边界后**第 2** 条到达（到达 p50 +2.28s） | 22.1% | 逐位相等 |
| 前 3 条都不等 | 55.3% | 「第 1 条 vs 官方」\|差\| p50 **0.145** / p90 **0.556** / p99 1.45 bps；88% ≤0.5bps、98% ≤1bps |

头两条合计 **44.7% ≈ 45.7%**（§1.2），即「对齐的那条落在第 1 还是第 2 位，取决于发布
延迟（p50 ≈1.3s）落在 1 秒格哪一侧」。剩下 55% 不逐位相等但差值很小（p90 0.56bps），
量级与「Chainlink 两次计算/取整的差」一致，不是错位一整个秒（相邻推送每秒变动
p50 0.049bps，错一秒会更分散）。

### 1.3 影响面（为什么说它是口径改动而非 P&L 杠杆）

在 14 天回测的 **625 条组合信号**上做换锚反事实：

| | 条数 |
|------|------|
| 换锚后掉出 | 11（1.8%） |
| 换锚后新增 | 9 |
| 净 | ≈ 0 |

结论：**不改 P&L 的量级**，改的是「锚与结算线是否同源」。真正的好处是 §2.5 的兜底——
锚缺失窗口从「整窗白丢」变成「照常判定」。

### 1.4 官方接口对**进行中**窗口可用

`GET /api/crypto/crypto-price?symbol=BTC&eventStartTime=…&endDate=…&variant=fiveminute&
twapEnabled=true&twapLookbackSeconds=60` 在窗口进行中即返回 `openPrice`（`closePrice:null`、
`cached:true`）；已完窗口偶发 429（上游 Chainlink 限流，SDK 仅对 429 重试故不生效——
这也是 `FetchTwapRanges` 里那两处 sleep 重试的来由）。

## 2. 规则

### 2.1 时间线（实测锚定）

| 时刻 | 动作 | 说明 |
|------|------|------|
| t=0 | `Latest()` + `AnchorUsableAtBoundary` → **初始 open**（到达口径）+ `PushNearest` 取单调门基准 | 用户拍板「可以暂时用 Latest」 |
| +1s 起 | **每秒**缓存重选（评估时刻口径），偏移单调下降才升级 | 边界那一秒的推送 p90 在 +2.28s 才到，定点单采会漏 |
| +2s | 官方尝试 ① | **只作无流值兜底**——此刻官方值尚未收敛（§9） |
| +5/+10/+20s | 官方尝试 ②~④ | 同上；拉开间隔吸收上游限流/慢响应；单次超时 10s |
| +40s | 官方尝试 ⑤ = **收敛点** | 一律采纳并覆盖（`SettleAfter`），即官方权威值；此后通道关闭 |
| 产出观测后 | **冻结** | 判定入口即终点，新值一律丢弃 |

### 2.2 单调门与 seed（必须）

t=0 用「最新到达」口径、+1s 起用「评估时刻」口径，两者在**乱序/重连补发**下不单调——
首个 pick 可能比 t=0 更差（如 −2s vs −1s）。故：

- `AnchorUpgradeOpts.SeedPickMs/SeedOK` = t=0 初值的**评估偏移**，作为单调门基准；
- 仅 `|pick| < |基准|` **严格变小**才送出（并列不升级）；
- t=0 无可用初值 → 无基准，首个命中即胜出（此时引擎 `anchor≤0`，本来就不产出观测）；
- seed 只在「缓存的最近评估条目**就是** t=0 采样到的那条」时采信（值相等判定）——
  不等说明 t=0 拿到的是补发/乱序的偏锚，此时不给基准，让通道首个命中直接覆盖。

### 2.3 官方尝试：跳过已流过的点，不补发；但**成功不结束**

到点判定用**绝对时刻**（边界 + Schedule[i]）。单次请求最坏耗时 = `FetchTimeout`(10s)，
会吃掉后面的 `+5s/+10s` 两个点——此时**只发一次**（对已到期点的最后一次），
不逐个补发：补发只会拿到早已失去意义的迟到值。

原实现「首个官方成功即终局」在 §9 的实测量出来之前是合理的（官方 = 真值），
但它会把 +2s 的**未收敛临时值**锁成终值。现改为：

- 每次成功都继续等下一个采样点，直到 Schedule 用尽；
- **`SettleAfter`（生产 = +40s）之前**的成功值只在「当前完全没有流值锚」（既无 t=0 初值
  也无重选命中）时送出——否则会把已知精确的边界那一秒推送（§9.3：与收敛官方差
  0.0002–0.0006bps）换成误差 p90 1.18bps 的临时值；
- **收敛点及之后**每次成功都送出（last-wins），最后一次即最终锚。

通道关闭条件相应改为：ctx 结束 / Schedule 用尽 / 硬停时刻到——**不再**因官方成功而提前关闭。

### 2.4 冻结：产出观测之后不认

`Engine.UpgradeAnchor` 在 `state != Watching`（产出观测、`rem==0` 终 tick，两种 Done）
时返回 false 并丢弃。理由：观测行已落盘，追溯改写会让「行上的 anchor」与「判定时用的
anchor」不一致（`touches_*` 与 `windows_*` 也对不上）。

### 2.5 兜底（三层）

| 情况 | 行为 |
|------|------|
| 官方收敛点成功（+40s） | 锚换成官方值（`anchor_src=official`），本窗照常判定 |
| 官方收敛点失败 | **保留流值锚**（t=0 初值或重选后的值，`anchor_src=stream`），照常判定 |
| 只有收敛点前的官方成功 | 有流值锚 → 丢弃官方值（它还没收敛）；无流值锚 → 采纳作兜底（`anchor_src=official`，聊胜于无） |
| 连初值都没有且全窗无可用缓存/官方 | 引擎 `anchor≤0` → 本窗不产出观测（等下一窗）。**无新增代码路径**——`ProcessTick` 的锚未就绪分支本来就是这个行为 |

## 4. 可见性字段

`winstats_*.jsonl`（每窗一行）：

| 字段 | 含义 |
|------|------|
| `anchor_init` | t=0 初值（0 = 无初值） |
| `anchor` | 最终生效锚（官方或流值） |
| `anchor_src` | `official` \| `stream` \| 空（无锚） |
| `anchor_pick_ms` | 最终流值锚的**评估偏移**（毫秒，可负；仅 `stream` 有意义）。**0 = 边界那一秒的评估值**（最好档）；非整千 = 本机与服务器时钟漂移 |
| `anchor_recovered_ms` | 最终锚取得时刻距边界（**仅升级过时非 0**；语义由 09-16 的「恢复时刻」扩为「升级时刻」） |

`windows_*.jsonl`（σ 贡献行）补 `anchor_src`：`RecentBlock` 只识**断档**、不识这种小幅
水平位移，σ 序列的口径切换必须在行上留痕。

`07_source_health_check.py` 新增 **【A2】锚来源**段：来源占比、`|最终锚 − t=0 初值|` 的
bps 分布（>0.5bps 的占比 = 旧口径明显偏的比例）、`anchor_pick_ms` 的整千倍数自检。

## 5. 与既有口径的边界

### 5.1 镜像红线（不动）

`cmd/btreplay` 只走 `BeginWindow` + `ProcessTick`，**不在升级路径上**——625 笔逐位一致
（`diff` 空）是本次改动的硬验收。

### 5.2 σ 的 close 口径**未改**（不对称已知）

窗口结束的 close 仍取 `lastTick.TwapPrice`（**到达口径**，评估时刻 ≈ `end − 1.5s`），
而 open 现在是官方/评估口径 → 本窗振幅 `|close − open|` 存在 ~1.5s 的微小不对称
（σ 尺度 ~0.3%，量级远小于 σ 自身波动）。**单独改动再议**（改它要动 σ 预热与镜像对账）。

### 5.3 覆盖前文表述

| 被覆盖 | 现在的口径 |
|--------|-----------|
| 09-16 文档 §0「取值来源 = 官方优先 + 窄窗口推送（\|到达时刻 − 边界\| ≤ 10s）」 | 改为**每窗常驻升级通道**：流值按评估时刻重选 + 官方轮询；「锚缺失」不再是一条独立分支 |
| 09-16 文档 §2.2 的 `abs` 判据（推送看**到达时刻**） | 判据改为**评估时刻偏移**（`anchor_pick_ms`），`abs` 语义保留在 `|偏移| ≤ PickTol` |
| 09-16 文档 §4 的 `anchor_src=push` | 改名 `stream` |
| `cmd/flip/main.go:565-570` 旧注释「官方开盘价 p50 偏差 0.08bps，复验按分布对比」 | 删除，改为 §1 的实测口径（该注释的数字不成立） |

### 5.4 未配置化

`anchorRefineSchedule` / `anchorPickTol` / `anchorRefineFetchTimeout` 继续做 `cmd/flip`
常量（沿用 `anchorRecoverAttempts` 等既有先例）。

## 9. 修法：官方值只认**收敛后**的采样（2026-09-18 当日追加）

§8.3 的实测推翻了原设想的「官方取到即终局」——官方接口头几十秒返回的是**未收敛的临时值**，
误差 p90 1.18bps（≈9.5 美元），**比这次要修掉的 t=0 误差还大**；而「评估时刻 == 边界」的
推送与收敛官方只差 0.0006bps（3 厘美元）。故锚的来源优先级按**时刻**分层：

```
t=0        Latest() 占位（到达口径，偏一档）
+1s 起     每秒按评估时刻重选（单调门：偏移严格变小才升级）→ 流值锚 ≈ 真值
+2/+5/+10/+20s  官方采样：**只在完全没有流值锚时**采纳（兜底）
+40s      官方采样（收敛点）：一律采纳并覆盖 → anchor_src=official
```

实现（`internal/feed/anchor_recover.go` + `cmd/flip/main.go`）：

| 项 | 原 | 现 |
|----|----|----|
| 官方成功 | 送出后**关通道**（终局） | 继续等下一个采样点，每次成功都送出（last-wins） |
| 早期官方值 | 无条件覆盖锚 | `SettleAfter`(=+40s) 前仅作无流值兜底（`opts.SettleAfter` + 「已有流值锚」判定） |
| 通道关闭 | ctx / 官方成功 / Schedule 用尽 | ctx / Schedule 用尽 / 硬停（**去掉「官方成功」**） |
| 日志 | `✅ 官方 open=…` 一条 | 早期丢弃时 `官方 +2s 采样值（边界后 +…）未到收敛点 +40s, 保留流值锚`；结束时 `官方 open 采样结束: N/M 次采纳`（N=0 时 ⚠️ 保持流值） |

**为什么收敛点取 +40s（最后一个采样点）而不是 +20s**：三窗实测收敛完成时刻分别落在
+6.9~+33.3s、+10.3~+40.4s、+2.8~+14.4s——**下界可能晚于 +20s**（15:40 窗），而 +20s 的
官方值一旦仍是临时值就会把已经精确的流值锚覆盖掉。取最后一个采样点则：

- 有流值锚（正常情形）→ 官方只在 +40s 覆盖一次，且那时两边同值；
- 无流值锚（WS 断流）→ 早期采样照常兜底（`SeedOK=false` ⇒ 无流值锚），+40s 权威覆盖；
- +40s 采样失败 → 锚停在流值对齐条目（= 真值），无损失。

**不去用「两次采样相同」当收敛判据**：15:40 窗的 +2.8s 与 +10.3s 返回的是同一个临时值
（80721.68），到 +40.4s 才跳变——同值不等于收敛。

**验收**：`go test ./internal/... -race` 全绿；`cmd/btreplay` 回放 **625 笔逐位一致**
（`ok n=625 WR 24.6% EV +0.633U/注 P&L +395.8U`）——升级路径不在镜像链路上，回测基线不动。
`01_backtest_r1.py` 四条基线不变（245/+264、530/+364、625/+396）。

## 8. 冒烟实测（2026-09-18 22:07 起，本机 paper）

### 8.1 引擎实跑（14 窗，`winstats_2026-09-18.jsonl`）

| 指标 | 实测 |
|------|------|
| `anchor_src` | 14/14 = `official`（每窗都取到官方值） |
| 官方取到时刻 | 边界后 **+2.45 ~ +6.44s**（多数落在 +2s 档；两窗走到 +5s 档） |
| `anchor_pick_ms` | 14/14 = **0**（即最终流值锚就是边界那一秒） |
| t=0 初值 vs 最终锚 | \|Δ\| p50 **0.24bps** / p90 **0.59** / max **1.23bps**，>0.5bps 占 **3/14 = 21%** |
| `windows_*` | `anchor_src` 字段已落盘（σ 序列的口径切换可查） |

⚠️ 本机 t=0 初值的评估偏移是 **−2000 ~ −4000ms**（走 1087 代理，TWAP 推送成批到达：
到达龄仅 200~1500ms，但评估时刻已落后 2~4 秒），比回测里的典型 −1s 更陈旧 →
这 21% 的 >0.5bps 占比是**本机代理环境的上界**，不代表生产环境。

⚠️ **这 14 窗跑的是当日的旧构建**（官方首次成功即终局，取到的是 +2.5s 的**临时值**）——
正因为如此，它们的 `anchor` 列恰好是 §8.3① 需要的「早期官方值」样本。

### 8.3 ⚠️ 关键发现：官方 `openPrice` 是**渐进收敛**的（§9 = 修法）

同一窗口、同一接口，**取数时刻不同值不同**。两支独立探针都指向同一结论：

**① 配对检验（n=17 窗，同一来源自比，无跨源歧义）**：引擎把每窗在 +2.5s 取到的官方值
写进了 `winstats.anchor`，事后对同一批窗口**再取一次**官方值（早已收敛）：

| 指标 | 值 |
|------|-----|
| 早期值（+2.5s）== 收敛值 | **4 / 17（24%）** |
| \|差\| p50 / p90 / max | **0.232 / 1.176 / 1.522 bps** |
| \|差\| > 0.5bps | 4 / 17 |

**p90 1.18bps ≈ 9.5 美元** —— 比这次要修掉的 t=0 误差（p90 0.59bps）**还大**。

**② 收敛曲线（`-mode drift`，同窗多时刻各取一次，实测耗时为准）**：

| 窗口 | 官方值随取数时刻的变化 | 对齐推送（真值） |
|------|------------------------|------------------|
| 15:35 | +6.9s **80718.92** → +33.3s 80721.40 → +62.9s 80721.40 | 80721.40 |
| 15:40 | +2.8s **80721.68** → +10.3s **80721.68** → +40.4s 80722.35 → +60.3s / +120.2s 80722.35 | 80722.35 |
| 15:45 | +2.8s **80647.31** → +14.4s 80644.32 → +30.3s 80644.32 | 80644.32 |

即：**收敛完成时刻落在 +10s ~ +40s 之间**（15:40 那窗到 +40.4s 才跳到真值，15:45 那窗
+14.4s 已收敛；15:40 的 +10.3s 与 +2.8s 还是同一个临时值——所以「两次采样相同」**不能**
当作已收敛的判据）。故收敛点取**最后一个采样点 +40s**。

**③ 对齐推送就是真值（`-mode aligncheck`，n=8）**：拿 §8.2 记录的「评估时刻 == 边界」
推送值 vs **现在**重取的官方值（必已收敛）：

| 指标 | 值 |
|------|-----|
| 8 窗的差 | 0.0002 ~ 0.0006 bps（绝对值 ≈ **3 厘美元**，打印到 `%.2f` 完全相同） |
| 对比：临时官方值的误差 | p90 **1.18bps**（≈ 9.5 美元） |

**结论：官方 open 要 ~+10~40s 才收敛，而「边界那一秒的推送」从一开始就是那个收敛值。**
原实现「官方首次成功即终局」因此把 +2s 的临时值锁成了终值 —— 这是本次修掉的东西（§9）。
