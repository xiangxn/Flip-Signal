# 空侧盘口：事件趋于确定后赢家侧整侧没有 ask（2026-09-24）

起因：用户看 `data/v4-tail/` 的纸面数据后提出「60s 检查点很多其实已经没有 ask 单了，
所以实盘很多可能都不能成交」，并要求两件事：**① 核实 SDK 的数据情况**、
**② Dashboard 里某一侧没有 ask 时不要再显示 0.99，改显示「—」**。
（用户明确：不要再去翻本地/回测数据，固定时间点上没 ask 是正常的，要的是**实盘活体**证据。）

本文是取证 + 修复记录。**结论先行**：

| 问题 | 答案（实测） |
|---|---|
| 最后几十秒到底有没有 ask？ | **赢家侧整侧为空**（不是没有消息）：4 个实盘窗里空侧起始 rem = **12 / 28 / 45 / 47**，一直空到收盘；对手侧（输家）始终有 ask，0.01 价位堆 3 万~20 万股 |
| 是 SDK 的锅吗？ | **不是**。`book` 是**整簿快照**，SDK（`market_monitor.go:286 onOrderBook`）原样解析，asks 空数组就是空 |
| 那 0.99 从哪来？ | **引擎自己的守卫**：`cmd/{flip,tail}` 的 WS 循环丢掉「单侧为空」的整簿消息 ⇒ 内存里留着**撤单前那一份旧簿**（常是 0.97~0.99），Dashboard 与判定都用它 ⇒ 已修 |
| 纸面数据的 0.99 是假的吗？ | **分两种窗**（§7 实盘复核后收窄）：空侧发生在 rem≤60 **之后**的窗（探针实测 rem = 12/28/45/47）⇒ 快照那一刻卖单还在，是真读数（样本 0.90×23 股、0.93×135 股、0.88×154 股）；空侧发生在 rem≤60 **之前**的窗 ⇒ 快照读的是**冻结簿**（旧守卫留下的是空侧前那一份），是**买不到的纸面价**。⚠️ 220 条 snap 行的镜像恒等式**分不出这两类**（两个 token 同一瞬间一起冻结，恒等式照样成立），故不构成"全部为真"的证据 |
| 实盘能不能成交？ | 有两个**硬约束**，见 §5：① 赢家侧卖单在最后 ~45s 被整侧撤空，挂单可成交窗口只有 ~10-15s；② 交易所 `minimum_order_size = 5 股`，而 `tail.stake=2U` 在 ≥0.80 时只有 2.02~2.5 股 ⇒ **低于下限**（flip 侧 2U@0.20 = 10 股不受影响） |

## 2. 决定性证据：WS 逐秒（窗口 1790250900，UP=yes 是赢家）

```
rem= 55 | UP n_asks=  7 ask=0.93 | DOWN n_asks= 92 ask=0.08   ← 档数开始被撤
rem= 52 | UP n_asks=  4 ask=0.96 | DOWN n_asks= 95 ask=0.05
rem= 48 | UP n_asks=  3 ask=0.97 sz=261 股 | DOWN n_asks=96 ask=0.04
rem= 47 | UP n_asks=  0 ask=0.00（空） | DOWN n_bids=0（空）    ← 整侧撤空, 两本书同时冻结
   ...  逐秒都有新消息（raw_age 0.1~2s），UP 的 n_asks 恒为 0 ...
rem=  1 | UP n_asks=  0 ask=0.00（空） | DOWN n_asks=99 ask=0.01 sz=65527 股
```

- 档数轨迹（rem 60→47）：`9 8 7 7 7 6 5 4 4 4 3 3 0` —— **慢慢撤、最后整侧撤空**。
- **镜像解释**：买 DOWN@p ≡ 卖 UP@(1−p)，所以「UP 空 asks」与「DOWN 空 bids」是**同一件事**
  的两面。两个 token **各有一侧为空** ⇒ 旧的 `len(Bids)==0 || len(Asks)==0` 守卫把
  **两个 token 的更新都丢掉** ⇒ 两本书一起冻结，**47 秒**。
- 引擎视角（`eng`）：`ask = 0.99` 一直挂到收盘，末秒**簿龄 46.9 秒**。
  **这就是 Dashboard 上的假 0.99**（用户看到的现象）。
- 空侧起点在不同窗不同：REST 探针独立复核到 **rem=12 / 28 / 45**（另三个窗），
  WS 探针这一窗是 **rem=47**。四窗一致：**赢家侧的 ask 侧在尾盘整侧消失**。

## 3. 根因与修复

```go
// 旧（cmd/flip/main.go:224、cmd/tail/main.go:363 同一句）
if book == nil || len(book.Bids) == 0 || len(book.Asks) == 0 { continue }   // ← 空侧消息被丢弃
```

`book` 事件是**整簿快照**（不是增量），空数组 = 市场真的没有那一侧。照存之后：

- `feed.bestAsk/bestBid` 返回 **0** ⇒ 两族引擎的**四档门控**（`UpBid/UpAsk/DownBid/DownAsk > 0`）
  把该 tick 判为无效 ⇒ 不会产出基于假卖价的信号（与回测宇宙同口径：回测数据里四档缺一即丢）；
- Dashboard 的 `yes_ask/no_ask` 变 0 ⇒ 前端已有的 `> 0 ? 价 : '—'` 分支生效，显示 **「—」**
  （tail 页的「⑤ 本窗过不过」还会显示「无有效盘口」）。**前端无需改动**——它本来就是对的，
  错的是喂给它的数。

改动清单：

| 文件 | 改动 |
|---|---|
| `cmd/flip/main.go`、`cmd/tail/main.go` | 守卫只留 `book == nil`（含「为什么不能再丢」的中文注释） |
| `internal/feed/pmtick_test.go` | 新增 `TestNewPMTickEmptySide`：空 asks/空 bids ⇒ 价格 0 且不通过四档门控（钉住前端「—」与引擎无效 tick 的数据契约） |

## 4. 一个与空侧**无关**的第二个陈旧来源：WS 慢消费者断线

探针期间 `MarketMonitor` 多次被服务端以 `close 1013: slow consumer: send buffer full`
断开再重连，期间**整簿消息停发**（`raw_age_ms` 尖峰）。窗 1790250900 里 `raw_age_ms > 1.5s`
的秒有 **41 秒**、最长 **12.4s**；冻结位置分散在窗口**中段**（rem 252/202/182/107-103/80-76/66-62…）。

- 这段时间引擎手里的书就是冻结的那本，**四档看起来完全正常**，
  `BookLatMs` 也**看不出来**——它是**接收时刻**算的传输延迟（`book.Latency = now − book.Timestamp`），
  不含此后累积的簿龄。
- 对 flip 的风险：冻结秒上若某侧 ask ≤ 0.20 且 rem > 180，触发会基于旧价成立。
  本次 2 窗样本**未出现**（该窗 UP 的 ask 在冻结前就已 ≤ 0.20，触发早已在更早的 tick 发生），
  但**未量化**。
- 对 tail 的风险：`rem ≤ 60` 的首个有效 tick 若正好落在冻结秒，快照的最优 ask（= 成交价口径）
  就是几秒前的价。本次样本里冻结段没压到 rem=60 那一秒。

**未做（口径问题，须单独一轮）**：把「读龄」纳入延迟闸（`MaxBookLatMs`）或落盘可见化。
回测 `MAX_LAT=300` 是同一口径的传输延迟，改判定条件 = 改口径 ⇒ 必须走回测，不在本次范围。

## 5. 对策略的含义（tail 实盘前必须先解决）

1. **`minimum_order_size = 5 股`**（CLOB `/markets/{condition_id}` 实测，`minimum_tick_size=0.01`、
   `neg_risk=false`）。`tail.stake=2U` 在 0.80~0.99 只有 **2.02~2.5 股** ⇒ 低于交易所下限，
   实盘挂单大概率被拒。（flip 侧 2U@0.20 = 10 股，不受影响。）
   ⚠️ 我没有凭证、也没有下任何单 ⇒ 「被拒」是元数据推断，**首次 live 必须先拿 1 笔小单验证**；
   若要满足下限，stake 需 ≥ 5U（0.99 处 5.05 股），等于把每笔风险从 2U 提到 5U——**这是用户决定**。
2. **成交窗口极短**：赢家侧卖单在最后 ~45s 内被撤空（连 0.99 档都不留）。快照那一刻（rem≈59-60）
   首档股数样本：`0.90×23`、`0.88×154`、`0.93×135`——2U 的股数够，但 GTC 挂上去只有 ~10-15s
   的窗口，之后整侧消失，未成交余量只能按闭市撤单（`trading.CancelAtClose`）处理。
   这与决策 #17 记的「live 成交样本天然偏向热门侧走弱」是**同一方向**的偏差，且更硬。
3. 纸面数据的 0.99 信号**不需要修正**（§2：那是 rem=60 的真实读数），但
   **live 会在 0.99 挂单 → 常常等不到成交** ⇒ 纸面 WR 99.6% 不能直接外推到 live。
   补充（§7 实盘复核）：若空侧发生在 rem≤60 **之前**，旧代码那一行的快照价来自冻结簿，
   不是"挂了单没成交"而是"根本没有对手方"——修后这类窗**一行都不产**。

- **Dashboard 已按用户要求显示「—」**：`no_ask` 那一格（前端 `> 0 ? 价 : '—'`）显示「—」，
  `no_bid` 仍是 0.99；判决卡显示「无有效盘口」。**不再有 0.99 的假卖价**。
- **0.00 是精确 0**，不是四舍五入：引擎自己的 `book_missing` 计数就是证据——它只在
  `!(UpBid>0 && UpAsk>0 && DownBid>0 && DownAsk>0)` 时累加（`internal/tail/engine.go:153`），
  本窗记 **78** 个 tick。
- **本窗一行快照都没产**（`frames 1` = 只有 rem=150 的帧行）：

| 窗口(UTC) | ticks | valid | stale | missing | 产出的行 |
|---|---|---|---|---|---|
| 12:10 | 299 | 161 | 138 | 0 | frame(150) + snap(60, price_low) + **scan(54, ok)** |
| 12:15 | 299 | 124 | 143 | 32 | frame(**71**) + snap(60, leg_out) |
| 12:25 | 299 | 148 | 73 | **78** | 只有 frame(150) —— rem≤60 段全程无有效 tick |

- 前两窗 `book_missing 0/32`（空侧在 rem≤60 之后）⇒ 快照是真读数；后两窗
  `book_missing 78/116` 且**快照闩锁从未推进** ⇒ 旧代码在这里会拿冻结簿产一条
  `snap hot_ask≈0.95-0.97` 的纸面信号，实盘买不到。**今天 2/2 的窗都是这种**
  （行情一边倒：rem≈130 时热门侧就已 0.95+），而探针四窗（rem 12/28/45/47）都是前一种
  ⇒ 比例随当日趋势摆动，不是固定频率。
- 顺带两条**独立**发现（都已在 §4 / §5 记过，这里给出实盘计数）：
  ① `book_stale` 25~143 / ≈299 tick（**8%~48% 的 tick 被 300ms 延迟闸判无效**），
     即慢消费者断线冻结的规模——它不进 `BookLatMs`（那是接收时刻的传输延迟）；
  ② 12:15 窗的帧行落在 **rem=71** 而不是 150：rem≤150 起的 79 秒里没有一个有效 tick
     （全 stale）——帧行"首个有效 tick"的语义在坏窗口会明显后移。

修后**快照样本会变少**（今天这类窗一行不产），§5.2 判决的 `n ≥ 800` 闸门会走得慢一些——
这是口径正确化的代价，不是退化：回测宇宙本来也要求四档齐全。
