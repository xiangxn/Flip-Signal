## 1. 止损腿的规格

```
触发 = 持仓侧 bid < 0.30  ∧  dev < −20 美元
出场 = 触发那一秒按**持仓侧 bid** 卖出（taker），P&L = shares·bid − STAKE
```

- `dev = sgn·(spot − anchor)`（美元，正 = 朝押注方向），与入场判定同一口径。
- **可评估 tick** = 延迟 ≤ 300ms ∧ spot 在场 ∧ **持仓侧 bid > 0** ∧ rem > 0。
  最后一条是硬前提：没有 bid 就卖不掉。这是 23 的 `win_ticks` 之外的第二套门
  （23 只管到 rem ≤ 150 为止的**判定** tick；止损要看**入场之后到闭市**的整条路径）。
- 阈值来自 `25` 的扫描平台（bid 0.25~0.30 × dev −20 整片同号），不是单点拟合。

## 2. 收益与胜率的变化（用户的核心问题）

| 口径 | 基线 | 加止损 | 变化 |
|---|---|---|---|
| 总 P&L（14 天，2U/注，n=2135） | **+35.67U** | **+46.11U** | **+10.44U（+29.3%）** |
| 胜率 · **官方 outcome**（引擎现行口径） | 95.97% | 95.97% | **±0** |
| 胜率 · **落袋**（卖出即定局） | 95.97% | 95.74% | −0.23pp |
| 亏损日 | 3 / 14 | **2 / 14** | −1 |
| 成对 bootstrap 95% CI（Δ） | — | — | **`[+2.24, +19.59]`** |

**两种胜率口径必须分开看**（用户前提「不能影响胜率」取决于用哪个）：

- **官方口径**：`settle_won` 不动 ⇒ WR 一位不变。但被止损且最终官方赢的那 5 行
  会显示「判赢却负 P&L」——引擎现行就是这么记的（同 flip 的方案 A 思路）。
- **落袋口径**：`fill ≥ 0.80` 而止损价 < 0.30 ⇒ **被止损行必然亏损** ⇒ WR 一定下降。
  这是记账的必然，不是策略恶化。

⚠️ 显著性判据必须是**配对 Δ 的区间**（`boot_delta`），不是止损后 P&L 的绝对区间——
后者与基线高度相关，基线点估计落在里面很正常。

## 3. 用用户判据复核：杀赢 vs 救输

触发 68 次（占信号 3.19%）：**杀赢 5 次 / 救输 63 次**。

出场价 `p̄` 处，救输一次省下 `shares·p̄`、杀赢一次多亏 `shares·(1−p̄)`
⇒ 打平所需 **救输:杀赢 = (1−p̄) : p̄**。

- 实际平均出场价 `p̄ = 0.139` ⇒ 临界比 **6.2 : 1**
- 实际 **63 : 5 = 12.6 : 1** ⇒ **留出 2.0 倍余量**
- 每笔：救输 **+0.289U**、杀赢 **−1.557U**
- Δ 分解：救输 **+18.22U** + 杀赢 **−7.78U** = **+10.44U**

⇒ 用户的否决条件（「杀赢导致亏的比不止损还差」）**不成立**，止损不放宽也不放弃。

**阈值建议用 `bid<0.25` 而非 0.30**：Δ 更高（+11.53 vs +10.44）**且**杀赢更少
（3 vs 5）。理由是不对称——杀赢的损失是无条件的（−1.56U/笔），救输的收益取决于
实盘可成交性（见 §6），所以宁可少杀。

## 5. 成交量专题：**不能提高止损精度**

### 5.1 整窗 BTC 总成交量（可从 tick 直接聚合）

```
V_win = Σ(bin.buy_vol + bin.sell_vol)    单位 BTC
信号窗 p10 / p50 / p90 = 23.8 / 66.0 / 204.9      极差 598×
```

三条独立证据都说它没用：

1. **对入场没有预测力**：ρ(V_win, 结算结果) = **−0.023**（秩相关，n=2135）。
2. **与 σ 腿半冗余**：ρ(V_win, sd) = **+0.579**——本窗实现的活动量有近 6 成
   被「前 18 窗的历史振幅」解释了。
3. **当开关也没用**（第四节全表）：只在**高**量窗止损，Δ 从 +10.44 掉到
   +1.67(p75) / −0.35(p90)，CI 全含 0；只在**低**量窗止损，Δ 只剩 +0.76(p25)
   （68 笔里 61 笔被关掉）。最好的一档（`<p90`，+10.78）只比不切好 0.34U。

### 5.2 用户假设：砸盘那一刻的**量比**

> 「不是简单聚合一个总量，是足秒累积，在被砸时看量比。比如被砸之前交易量 20 BTC，
> 连续砸了 40 BTC，这就有可能是有什么事件导致的，可以提高止损精准吧？」

测法：最近 k 秒的成交量 ÷ **被砸之前**的基准速率（基准**不含**被砸的那 k 秒，
否则放量会把自己归一化掉——这正是第一版 `V_burst` 失效的原因）。

**方向对，但强度不够、且正好在止损那一刻消失**——这是本次最值得看的结果：

| 跌破价位 | 样本 | 量比 AUC | bid 跌幅 AUC |
|---|---|---|---|
| 0.60 | 179 | **0.574** | 0.583 |
| 0.50 | 148 | 0.532 | 0.557 |
| 0.40 | 128 | 0.493 | 0.522 |
| **0.30**（止损在这里触发） | 112 | **0.482** | 0.484 |

- 效应量（跌破 0.60 的 179 笔按量比分三档）：高量比档最终输 **60.0%**、
  低量比档 **43.3%**——差 16.7pp，**1.8σ，p ≈ 0.06，不显著**。
- 判别力**逐级衰减**：0.574 → 0.532 → 0.493 → 0.482。被砸得越深，量比的解释力越弱。
- 道理也说得通：砸到 0.60 时「是不是真有事」还有悬念，放量确实是信息；
  砸到 0.30 时**事情已经发生完了**，量比早被价格吸收干净。

⇒ 量比测得出「这次砸盘凶不凶」，但测不出「砸完之后会不会弹回来」——而后者才是
止损要判的东西。**这个维度上没有可落地的改动。**

> ⚠️ 6b 那张表的样本量是量比专题里唯一够用的（179/148/128/112 笔）；第 25 号脚本
> 早先测的「触发止损那一秒的秒量」AUC 0.485~0.499 也是同一结论。

### 5.3 顺带浮现的一条线索（是**另一条策略**，不在本次范围）

持仓期间跌破 0.60 之后，最终输的概率是 **48%（86/179）**。在 0.60 出场 vs 死扛的
赔率结构完全不同——出场价 `p` 处临界比 = `(1−p):p`，**0.60 处只有 0.67:1**
（vs 止损在 0.30 的 5.5:1）：杀错一次只亏 0.40/股，救对一次省 0.60/股，几乎对半开
就够本。这与「止损在 0.30」是两个数量级上不同的赌注。

⚠️ 但它是**早退策略**、不是止损腿，且同样吃决策 #21 的对手方上界（0.60 处还有没有
买盘，同样未经验证）⇒ **须单独立项，不要顺手加**。

## 6. ⚠️ 上界声明（读数前必读）

25 号脚本文件头列了三条，这里再强调最硬的一条：

1. **对手方（决定性）**：所有离线 Δ 都假设触发那一秒有 bid 可吃。但决策 #21 的
   活体取证（SDK WS + 公共 REST 双通道）证明：**尾盘「押最终输家」的那条腿被整侧
   撤空**（BTC 探针四窗空侧起始 rem = 12/28/45/47；ETH 首采 rem ∈ [0,34] / [0,79]）。
   止损要出场的那一刻，正是持仓从赢家变成输家的那一刻。
   历史 14 天里「持仓侧 bid == 0」出现 **0 次**——那是旧采集守卫丢弃空侧消息的
   **构造性产物**，不是市场属性。⇒ **全部 Δ 都只是上界。**
2. **滑点**：无。按 bid 全额成交；实际 taker 卖出会打折。
3. **交易所下限**：CLOB `minimum_order_size = 5 股`，而 `tail.stake=2U` 在 ≥0.80
   只有 2.02~2.5 股（决策 #21 ②）——tail 上 live 前必须先解决 stake ≥ 5U。

### 6.1 应对：持仓监察（只记录，不改判定）

`internal/tail/hold.go` 新增第四族记录 `tailhold_YYYY-MM-DD.jsonl`：

- **信号成交后逐 tick 一行**，记持仓侧盘口（bid/ask + **前 5 档深度**）、dev、spot、
  盘口延迟，外加一个纯派生标记 `stop_cand`（= 26 号脚本的止损条件，方便分析时
  一步筛出「若真挂了止损，这一秒会不会触发」）。
- **门控与判定路径刻意不同**（这是它存在的全部理由）：
  `rem > 0` ∧ 延迟 ≤ 300ms ∧ spot > 0 ∧ 锚可用——**不要求持仓侧 bid > 0**
  （bid == 0 正是要观测的东西）、**不要求四档齐全**、**不要求 rem ≤ 150**。
- **硬边界三条**：只记录（不进 P&L / 熔断 / 胜率 / 任何判定）；不碰引擎状态
  （纯函数 + 独立前缀 `tailhold_`，与 `tail_`/`tailwin_`/`tailstats_` 互不沾染，
  决策 #9 红线）；落盘失败只记日志、不上抛主循环。
- 深度字段（`hold_bid5`/`hold_ask5`）由 `cmd/tail` 从 SDK 簿现算回填——`internal/tail`
  零外部依赖，不引 SDK。

**为什么必须记深度**：`minimum_order_size = 5 股`，所以「bid 存在但只有 3 股」与
「没有 bid」对实盘是一回事，价格字段分辨不出来。

**读法**：跑一两周后，看**触发止损的那些时刻**（`stop_cand=true`）里
`hold_bid == 0` 的占比、以及 `hold_bid5` 的分布。
- 占比低 + 深度够 ⇒ §2 的 +10.44U 大致可信，可以认真考虑上止损；
- 占比高 ⇒ Δ 要按实际能成交的比例打折，甚至可能归零——那时**不上止损**。
